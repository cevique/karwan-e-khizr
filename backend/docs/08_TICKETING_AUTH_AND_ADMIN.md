# 08 — Ticketing, Fares, Authentication, and Admin

**Scope note:** this document specifies backend APIs and data
contracts only. Any admin dashboard UI, ticket-purchase UI, or
validator-scanning UI is a frontend responsibility, owned separately —
see `00_PROJECT_OVERVIEW.md` §"Backend/frontend boundary". These are
first-class backend components, not incidental plumbing — the backend
must support a real purchase→QR→validate API flow, not just a route
planner.

## 1. Fares — explicit statement, do not overclaim

Fares must be **DB-driven** via a `FareRule` model (`base_fare`,
`per_leg_fare`, `currency`, `name`), read from the database with an
in-code default fallback only when no rule row exists. The computation
is a flat per-boarding formula: `0` for an all-walking journey,
otherwise `base_fare + per_leg_fare × (ride_leg_count − 1)`.

**Explicitly NOT:** distance-based, route-based, agency-based, or
sourced from any external fare API — no such API is known to exist.
This is a deliberate, documented simplification.

**FUTURE:** distance-based or route-based fares, once real per-route
distance data exists (blocked on the same route-geometry coverage gap
described in `04_TRANSIT_DATA_AND_DOMAIN_MODEL.md`) — do not build this
ahead of that data existing.

**AI boundary (see `06_AI_AND_VOICE_ARCHITECTURE.md`):** any fare
figure narrated by the conversational agent must be copied verbatim
from a `get_fare_quote` tool result, never estimated or generated by
the LLM.

## 2. Ticketing + QR

### State machine

```
ACTIVE → USED
ACTIVE → EXPIRED   (lazy expiry, evaluated at read/validate time —
                     not a background sweep; an acceptable
                     simplification since every read path re-derives
                     effective state)
ACTIVE → REVOKED
```

### Design requirements

- Ticket creation must compute fare **server-side** from
  `ride_leg_count`, never trusting client-supplied fare/leg data.
- QR payload must be a **signed, opaque token** encoding only
  `ticket_id`/`user_id` — verified server-side before any ticket-state
  lookup. No ticket fields may be directly readable from the QR itself.
  This prevents forgery and keeps the backend as the sole source of
  truth.
- Validation (`validate_ticket`) must be **atomic**: ticket state is
  checked and transitioned in a single transaction, preventing double-
  validation/replay of the same ticket.
- Ownership must be enforced: a ticket's owner and the QR's claimed
  owner must match (a tamper check).
- Payment is a separate concern (see §3), decoupled behind a
  `PaymentProvider` interface — ticket creation must only proceed if the
  payment call succeeds.

### Entity design

**DECISION REQUIRED, recommendation stated:** a three-entity model
(`Ticket`, `Payment`, `TicketValidation`) is one possible design, but a
simpler design is recommended: `Ticket` as the single persisted entity,
payment as an ephemeral provider call (not a persisted record),
validation as a `Ticket` state transition (not a separate table). This
avoids unnecessary schema complexity while the payment layer is mocked.
Introducing a separate `Payment` table is **FUTURE** — justified once a
real payment provider is integrated and its own transaction records
need independent persistence/querying (e.g. for reconciliation).

## 3. Payments

A `PaymentProvider` interface is required, with a default
implementation that always succeeds (no real transaction, no real money
movement) so the ticketing flow is fully demonstrable without a real
payment integration. No real payment provider is assumed to exist —
none should be fabricated.

**FUTURE:** a real payment provider (e.g. a Pakistani payment gateway)
implementing the same interface.

## 4. User accounts

- Registration, login, JWT-based sessions, bcrypt password hashing are
  required.
- Two roles: `passenger`, `admin`.
- Refresh-token rotation, password reset/change, and email verification
  are **FUTURE** — not required for initial delivery, but the account
  model should not preclude adding them later.

Password change/reset is a reasonable secondary-priority addition if
time allows — see `10_IMPLEMENTATION_HANDOFF.md` for sequencing.

**FUTURE:** saved routes, favorite stops, ticket/journey history beyond
the basic ticket list, per-user default routing preferences.

## 5. Admin

An admin-gated API is required for data operations (seed, import, graph
rebuild, trip generation), authenticated via a `require_role(admin)`
pattern.

**Prioritized for initial delivery:**
- Realtime/simulation status view (which trips are running, vehicle
  count) — demonstrates the simulation is live and controllable.
- Ticket inspection (list/lookup by code/status) — for demoing the
  validate flow live.
- Data-quality view (which stops are `UNKNOWN`, which routes lack
  geometry) — a genuinely useful "here's what's real vs. still being
  built" honesty panel.
- **AI/ETA pipeline health panel** — API-exposed status of whether the
  Request #1 (`IntentLLMProvider`), Request #2
  (`JourneyResponseLLMProvider`), Groq Whisper
  (`SpeechToTextProvider`), and `ETAPredictor` connections are live, and
  which primary/fallback provider is currently active for each. Cheap
  to build (one health-check per external dependency, exposed via
  `GET /ai/health` per `03_BACKEND_ARCHITECTURE.md` §3), directly
  supports the "graceful degradation" property described in
  `06_AI_AND_VOICE_ARCHITECTURE.md`. Any visual presentation of this
  data is a frontend concern.

**FUTURE:** full stop/route/fare CRUD, full user management — valuable
but not required for initial delivery.

## 6. Security requirements specific to this area

- Rate limiting on `/auth/login`, `/auth/register`, and
  `/tickets/validate` is required.
- `SECRET_KEY`/JWT signing key must come from environment, never
  hardcoded.
- The admin router auth pattern (§5) must be applied consistently to
  every admin endpoint.
- Any endpoint that can mutate simulated vehicle/trip state must be
  authenticated on any hosted deployment. Unauthenticated developer/
  demo control endpoints, if provided for local development
  convenience, must never be exposed on a publicly reachable
  deployment.
