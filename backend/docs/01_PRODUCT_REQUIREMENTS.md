# 01 — Backend Requirements

**Scope note:** this document specifies backend requirements only —
what data and API contracts the backend must provide. It does not
specify how any client renders, presents, or interacts with that data;
that is the responsibility of the frontend, owned separately (see
`00_PROJECT_OVERVIEW.md` §"Backend/frontend boundary").

All requirements below are **REQUIRED** unless explicitly marked
**FUTURE** or **DECISION REQUIRED**.

---

## 1. Journey planning requirements

1.1. The backend must accept an origin and a destination as free text
(place/stop name) or as coordinates, and return one or more suggested
journeys via `POST /transit/journeys/search`.

1.2. A journey response must be composed of ordered legs: walking,
riding a specific route between two stops, and transfers between
routes. Each leg must include duration, distance (for walking), and
route/stop identifiers (for riding), plus GeoJSON geometry sufficient
for a client to render it on a map.

1.3. The backend must accept routing preferences either as explicit
structured filter fields (for direct/manual API calls) or as natural
language processed through the two-stage AI pipeline (see
`06_AI_AND_VOICE_ARCHITECTURE.md`). Both paths must resolve to the same
fixed, backend-supported filter set.

1.4. Supported filters: routing objective (`fastest` /
`fewest_transfers` / `least_walking`), maximum walking distance,
maximum number of transfers. **DECISION REQUIRED, data-dependent:**
cheapest-route optimization and earliest-arrival/latest-departure
solving are desirable but require time-dependent routing and
fare-aware ranking respectively — see `10_IMPLEMENTATION_HANDOFF.md`
for sequencing. Accessibility filtering is **FUTURE** — no
accessibility data field is defined in the initial data model; do not
fabricate one.

1.5. A journey search response must return multiple ranked candidate
journeys (not just one), reflecting different objectives.

1.6. Where real timetable data exists (see
`04_TRANSIT_DATA_AND_DOMAIN_MODEL.md` for current coverage), a journey
search with a departure time must reflect the actual next scheduled
trip, not a flat duration estimate. Where no timetable exists, journey
timing must use a documented, honest estimate (route length ÷ an
assumed average speed) — never a fabricated schedule.

## 2. Conversational / voice API requirements

2.1. The backend must accept a typed request in English, Urdu, or
Roman Urdu, or a mix, via the conversational endpoint (`POST
/ai/converse`), and return a validated journey search result plus a
natural-language response.

2.2. The backend must accept an audio payload (speech) via the same
endpoint, transcribe it (Groq Whisper), and process the transcript
through the identical pipeline used for typed text — see
`06_AI_AND_VOICE_ARCHITECTURE.md` §"Voice and text converge into the
same pipeline". Urdu/Roman Urdu voice transcription quality is subject
to Groq Whisper's actual language support and must be verified at
implementation time; typed Urdu/Roman Urdu is not affected by this and
must work regardless.

2.3. When a request is ambiguous (an unresolvable place name, a missing
required field), the backend must return a structured
clarification-needed response (with the natural-language clarifying
question generated by Request #2) rather than guessing or fabricating
a value.

2.4. Every fact stated in the natural-language response (a time, a
fare, a delay, a distance) must be traceable to a value present in the
authoritative journey JSON produced by the backend journey engine — see
`06_AI_AND_VOICE_ARCHITECTURE.md` §"Backend authority principle" for
the enforcement mechanism. This is a hard requirement, not a
nice-to-have.

2.5. **FUTURE, out of initial scope:** multi-turn conversational
follow-up referencing a prior turn's result within the same session
(the current specification defines one command → one response cycle;
session-based follow-up is a documented extension point, not part of
the required two-stage pipeline).

## 3. Map/geospatial data requirements (backend responsibility only)

3.1. The backend must expose: stop locations, route geometry (GeoJSON,
where generated), live vehicle positions, and full journey-leg
geometry — everything a client needs to render a map, without the
backend rendering anything itself.

3.2. `GET /transit/stops/{id}` must return the routes serving that
stop. `GET /transit/routes/{id}` and `/routes/{id}/geometry` must
return a route's path and stop sequence, where geometry exists.

3.3. A journey search response must include full geometry for every
leg (walking and riding) in a single response — a client must not need
a separate API call per leg to render a selected journey.

3.4. Vehicle-position responses must include position, heading/bearing,
status, and a `source` label (`"simulated"` or `"realtime"`), plus ETA
data — sufficient for a client to distinguish and render vehicle
markers without additional backend calls.

3.5. Basemap selection, tile rendering, and all other purely visual
map concerns are explicitly **out of scope for the backend** — see
`05_ROUTING_AND_GEOSPATIAL.md` for the backend's geometry/coordinate
responsibilities and its boundary with map rendering.

## 4. Realtime / simulation requirements

4.1. Live vehicle positions must be generated by simulation where no
live vehicle feed exists (see `07_REALTIME_SIMULATION_AND_ETA.md`),
using real route geometry and real/estimated timing, and must be
**honestly labeled** as simulated via the API's `source: "simulated"`
field. If a real vehicle feed is ever connected, its positions must be
labeled `source: "realtime"`.

4.2. A vehicle's ETA at its next stop, and any current delay relative
to schedule, must be exposed via API, computed from the simulation (or
real, once available) state.

4.3. **FUTURE:** a predicted ETA field, returned alongside (never
replacing) the deterministic baseline — see
`07_REALTIME_SIMULATION_AND_ETA.md`.

## 5. Ticketing requirements

5.1. From a selected journey, the backend must support ticket purchase
for a computed fare via API.

5.2. Payment must be simulated (mocked) initially — no real payment
provider is assumed to exist. The payment step must be behind an
interface so a real provider can be added later without changing
ticket logic.

5.3. A successful purchase must produce a ticket with a signed, opaque
QR payload — never raw ticket data encoded directly in the QR.

5.4. A validation endpoint must accept a QR code (or manually entered
code) and return an authoritative VALID/INVALID result, atomically
marking a valid ticket as used (preventing double use/replay).

5.5. The backend must expose a user's ticket history and any currently
active ticket via API. See `08_TICKETING_AUTH_AND_ADMIN.md` for the
full ticketing specification.

## 6. Account requirements

6.1. The backend must support registration and login (email/password
or equivalent) via API; sessions are JWT-based.

6.2. A logged-in user's tickets must be scoped to their account
(ownership-enforced server-side).

6.3. Two roles exist: passenger and admin.

## 7. Admin API requirements

7.1. The backend must expose authenticated admin endpoints for system/
data status: which stops have coordinates, which routes have geometry,
which trips/vehicles are currently simulated as running, ticket
inspection by code/status. Any admin dashboard UI consuming these
endpoints is a frontend responsibility.

7.2. **DECISION REQUIRED, scope-dependent:** full CRUD endpoints for
stops/routes/fares/users are **FUTURE**; the initial admin API surface
is read/status-oriented (§7.1), not editing-oriented — see
`10_IMPLEMENTATION_HANDOFF.md` for sequencing.

## 8. Non-functional requirements

8.1. **No AI-produced value (route, fare, ETA, delay, timetable) may
reach the client without having passed through the deterministic
backend journey engine first.** This is the single most important
non-functional requirement in this document — see
`02_SYSTEM_ARCHITECTURE.md` §"AI / deterministic boundary" and
`06_AI_AND_VOICE_ARCHITECTURE.md` §"Backend authority principle".

8.2. The AI pipeline must have a defined fallback behavior so the core
journey-planning-and-ticketing API remains usable (via direct
structured requests) if the Intent LLM, Response LLM, or Groq Whisper
is unreachable, rate-limited, or unconfigured — see
`06_AI_AND_VOICE_ARCHITECTURE.md` §"Ambiguous input and failure
handling".

8.3. Simulated/estimated data (vehicle positions, fares where static,
non-canonical timetables) must never be presented as officially
sourced or real-time without labeling.

8.4. The backend must not fabricate coordinates, route geometry, stop
sequences, or timetables where real data is missing — a documented gap
is preferred over an invented value, everywhere in the system,
including inside AI-generated narration.

8.5. End users must never supply, see, or configure any AI provider
API credential (Gemini, Groq, or otherwise). All AI provider
credentials are server-side project secrets — see
`03_BACKEND_ARCHITECTURE.md` §5.1.

## 9. API-level command flow (summary — see
`10_IMPLEMENTATION_HANDOFF.md` §"End-to-end flow" for the full sequence,
and `06_AI_AND_VOICE_ARCHITECTURE.md` for the complete pipeline
specification)

- **Plan a journey (voice or text, via `/ai/converse`):** client sends
  typed text or an audio payload → backend transcribes (voice only),
  extracts structured intent (Request #1), runs the deterministic
  journey engine, generates a natural-language response (Request #2) →
  backend returns `{structured_journeys, text_response}`.
- **Plan a journey (direct, via `/transit/journeys/search`):** client
  sends a structured request directly, bypassing the AI pipeline
  entirely → backend returns the same structured journey response.
- **Buy a ticket:** client selects a journey → `POST /tickets` with
  fare confirmed server-side → simulated payment → QR ticket payload
  returned.
- **Validate a ticket:** `POST /tickets/validate` with a scanned/typed
  code → VALID/INVALID returned, ticket marked used if valid.
- **Admin status check:** authenticated admin client calls admin status
  endpoints for live simulation/ticket/data state.
